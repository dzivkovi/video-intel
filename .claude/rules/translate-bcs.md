# BCS subtitle translation (scripts/translate_video.py)

Moved verbatim out of the root `CLAUDE.md`. This subsystem is deliberately NOT part of the video-intel pipeline, so its guidance loads only when you work on it. Same content, same authority.

**Bracketed timestamp shapes are defined ONCE, and the MINUTE field is UNBOUNDED (issue #197).** `TS_HOURS` / `TS_MINUTES` / `TS_MINUTES_IN_HHMMSS` / `TS_SECONDS` plus `HHMMSS_BRACKET_RE` / `MMSS_BRACKET_RE` are the single definition; three consumers build from them (`extract_last_timestamp_seconds`, `detect_overshoot`, `TRANSCRIPT_TIMESTAMP_RE`). Same defect class as issue #195 in `video_intel.py`, filed on shape alone. A `\d{1,2}` minute field does not mis-match a `[100:30]` stamp - it does not match AT ALL, so each consumer failed in its own way. **State the reachability exactly, because the first cut of this entry did not and a review pass traced it:**

- **`TRANSCRIPT_TIMESTAMP_RE` is the one with a demonstrated real-user path.** It **rejected** a transcript whose stamps are all past 99:59 as "does not look like a transcript produced by video_intel.py transcript" and exited 1 - reachable through a clipped-tail transcript (`transcript --url --start 1:40:00`), and video-intel's own `_captions_timestamp` renders unbounded `MM:SS` systematically (#195). This is what the fix repairs for an operator.
- **`extract_last_timestamp_seconds` and `detect_overshoot` are called ONLY from the captions path and the single-request video path**, never from `--from-transcript`. Both of those paths are contractually `[HH:MM:SS]`: `prompts/translate-bcs.md` mandates `Format: [HH:MM:SS]`, and `youtube_captions.py` renders the block zero-padded. A bare `[MM:SS]` past 99:59 reaching either helper requires Gemini to abandon the format it was handed - possible, not routine. Do not restate this as a guaranteed false truncation warning: on a real full-video translation the pre-fix value would be the last sub-100-minute stamp (5999), still wrong but not 0, and 0 arises only on a clipped input.
- **The genuinely reachable defect in that pair is the `\d\d` parity bug** (item 3 below), which silently disabled the overshoot guard for any single-digit-hour `[1:05:30]` stamp on the captions path. That is the strongest non-`TRANSCRIPT_TIMESTAMP_RE` half of this fix, not a footnote.

Six things reviewers must protect. (1) **The HOUR field stays `\d{1,2}`** - it is hours, 99 is already absurd, and widening it would let a legacy malformed `[120:05:30]` parse as 120 hours instead of failing to match; `normalize_timestamp` is what repairs that shape, and a test pins that `[120:05:30]` still returns `None`. A 25-input old-vs-new differential confirmed the widening is strictly monotone: nothing that parsed before stopped parsing, no value changed, and the two patterns are never both matching on any input. (2) **`\d+`, not `\d{1,3}`** - a capped field just moves the cliff to 16h40m, and multi-hour conference days are exactly the affected population (#195 invariant 3). **The drift guard must actually catch `{1,3}`**: the first cut's guard regex matched only the two literal shapes the PR deleted, so a reviewer reintroduced a `\d{1,3}` literal and it passed. It now matches any counted `{N}` / `{N,M}` first field, and `test_the_guard_regex_actually_matches_a_known_bad_literal` feeds it known-bad samples - without that companion, `test_the_walk_is_not_vacuous` proves only that the CONSTANTS exist, never that the SEARCH pattern still matches anything. (3) **`detect_overshoot`'s two patterns were even narrower (`\d\d`, exactly two digits) than its own docstring claimed** - it promised parity with `extract_last_timestamp_seconds`, which accepts `\d{1,2}`, so a single-digit hour matched one and not the other. That claim is true now, and the parity test probes RECOGNITION directly (`last_input=-1` **with `tolerance_seconds=0`**, so a `None` return can only mean "not recognized"). The obvious `-1` alone leaves the default 30s tolerance in place, which is why the first cut's assertion carried an `or via_extract == 0` escape clause and failed on a healthy `[00:20]`. (4) **`TS_MINUTES_IN_HHMMSS` is its own constant, not `TS_SECONDS` reused.** The middle field of `[HH:MM:SS]` is semantically minutes; borrowing the seconds constant means a future change to the seconds field silently moves the minute field too - the exact coupling class this change exists to prevent. (5) **Three inline bracketed literals are deliberately NOT rewired, and each carries a `# timestamp-literal-ok:` marker naming why** - two in `apply_timestamp_offset` (they run AFTER `normalize_timestamp`, so they must accept the repaired shape) and one in the stitch monotonicity check (it reads the output of `apply_timestamp_offset`'s own zero-padded writer, which is the checker-uses-the-writer's-shape rule, not a fourth copy of the input grammar). `test_the_exemptions_are_explicit_and_bounded` pins the count at three, so marking a fourth has to be a deliberate act. Known limit: the marker lookback is a 6-line window, so one marker can excuse an immediately adjacent literal - the count test is what closes that, not the window. (6) **Operational separation is unchanged** - the fix adds no `video_intel` import, and the test that proves it walks the AST rather than scanning for a substring, because the module legitimately MENTIONS `video_intel.py` in the `--from-transcript` help text. The permitted shared imports are `timestamp_utils` (stdlib-only by contract), `gemini_common` and `youtube_captions`. The AST walk cannot see `importlib.import_module("video_intel")` - verified, the suite stays green - so read it as a drift catcher, not a sandbox.

**Why this does not build on `timestamp_utils.TIMESTAMP_TOKEN_PATTERN`, which calls itself "the one regex source" (#195).** The two definitions genuinely disagree, and the disagreement is the point: `[120:05:30]` and `[100:05:30]` MATCH `TIMESTAMP_TOKEN_PATTERN` and must NOT match `HHMMSS_BRACKET_RE`, because in the translator that malformed minutes-in-hour shape has to fall through to `normalize_timestamp` for repair rather than parse as 120 hours. Nothing about operational separation blocks the import - `translate_video.py` already imports that module. A future "consistency" pass that unifies them would break the repair path silently. Test contract: `tests/test_translate_timestamp_minutes.py`.

**`--from-transcript` WINDOWS, honors `--start`/`--end`, and never reports a hole as success (issue #206).** Three defects from one live run: a 1h58m interview (138 KB, 683 entries) sent as ONE streamed request died at `503 UNAVAILABLE. The request timed out.` about 5.5 minutes in, having translated roughly the first 46 minutes, and the partial was discarded while the log said it had been preserved. Ten things reviewers must protect - **and note that items 1, 5 and 6 exist because the first cut got them wrong and a review pass caught it by EXECUTING the CLI, not by reading the diff.**

1. **The parser must not refuse the flags the feature implements.** `--start`, `--end` and `--chunk-minutes` were rejected by three `parser.error(...)` calls dating from when this path had nowhere to apply them. The first cut threaded all three through `_translate_from_transcript` and **left the refusals standing**, so the entire feature was unreachable from the CLI (`exit 2`, zero Gemini calls) while all 18 unit tests passed - every one of them called the function directly. This is the standing "a helper tested but never proven called" rule one layer up: the wiring was not a missing call, it was an argument parser rejecting the call before it happened. `TestTheCliActuallyReachesTheFeature` drives `main()` and is the guard; a diff that adds a mutual-exclusion for these flags must delete it.
2. **Windows cut on cue boundaries, never mid-entry.** An entry runs until the next timestamped line, so a SCREEN block or OCR line inherits its entry's window. A cue exactly on a boundary starts the NEXT window. Concatenating every window must reproduce the input byte-for-byte - proved across `chunk_minutes` in {1, 5, 10, 20, 10^6}, unparseable stamps, empty and whitespace-only bodies, non-monotonic cues, and a missing trailing newline.
3. **The boundary advances in a LOOP, not by one step.** After a long silence the boundary must catch up in one go; advancing once per cue turns a transcript with a three-hour gap into one Gemini call per subsequent cue. The original test for this asserted "no empty windows", which the splitter cannot produce (a window is only emitted when it has content), so deleting the advance loop left it green. The replacement asserts the COST property - a gap-then-dense fixture must yield 2 windows, not 4.
4. **The preamble goes to window 1 ONLY.** Feeding the title/URL/date header to every window stitches N translated headers into one file. A transcript with no preamble must not lose its first cue to the split.
5. **`--start`/`--end` filter BEFORE any Gemini call, and the end is EXCLUSIVE.** The first cut ran `translate_title` - a paid call - above the range filter, so `--start 200 --end 210` on a two-hour transcript billed a title translation and then exited 1 with nothing to show. Measured, then fixed; standing probe-before-you-pay rule. The exclusive end matches `split_transcript_into_windows`, and it is what makes consecutive ranges TILE: `--end 45` then `--start 45` covers every cue exactly once. An inclusive end duplicates the boundary cue across two runs - and a series of adjacent ranges is precisely the recovery this feature documents for a missing window.
6. **A window that returns nothing is a HOLE, and it must be visible on every surface.** The first cut logged it and carried on to a clean `exit 0` with a "Written to ..." line, so a 20-minute gap in the middle of an interview left no trace in the file, its header, or the exit code. **That was a NEW failure mode this feature introduced** - pre-#206 a single empty response was `sys.exit(1)`. Continuing is still right (the other windows are real, billed translation), but the gap now gets: an `<!-- MISSING: ... -->` comment in place, a `## Incomplete translation` notice in the header naming each missing range and the `--start`/`--end` recovery, and `EXIT_INCOMPLETE` (3), mirroring `video_intel.py`'s `EXIT_PARTIAL` from issue #129. The header notice is SEPARATE from the pre-existing truncation notice on purpose: that one keys on an observed-vs-requested END ratio and structurally cannot see a hole in the MIDDLE, because such a run ends exactly where it should. An earlier hole also outranks any later window's own `finish_reason`, or window N+1 succeeding with STOP would let the header claim a clean run over a file with a gap in it.
7. **One `tmp_file` handle for the whole run, opened BEFORE the first call, closed exactly once.** The stream handler logs "Partial output preserved in .txt.tmp file"; before #206 this writer created its tmp only after a successful return, so that message was simply false here. **The test for this must make the stub write PER WINDOW.** The first cut's stub wrote only on the call that failed, so reopening the handle per window - truncating away windows 1..N-1, destroying two thirds of a billed translation - left all 18 tests green. A stub that exercises only the failure path cannot detect a defect on the success path; that is the PR #136 stub-agrees-with-its-own-assertion rule applied to a file handle instead of a path. The assertion names every window that must still be in the tmp, not merely that it is non-empty.
8. **`_merge_usage` sums across windows.** Mutating it to last-window-wins - the exact under-report-by-N this item forbids - left 244 tests green, because nothing read the token count back. It has direct coverage now.
9. **`--chunk-minutes <= 0` is refused at the PARSER.** The splitter raises for it, but the splitter runs after `translate_title`, so a library caller would get a traceback and a bill. Same probe-before-you-pay placement as item 5.
10. **The advertised recovery must be a command the CLI ACCEPTS, and `recovery_range_minutes` is the one place that computes it (Codex peer pass).** Window bounds are exact SECONDS from cue timestamps; `--start`/`--end` take integer MINUTES; and `--end` is exclusive while the FINAL window's end IS its last cue. So the naive instruction was untypeable at best (`[00:20:07 - 00:40:09]`) and selected NOTHING at worst (`--start 40 --end 40` on a one-cue tail window). A recovery that cannot work is the same defect as the `Raise --limit` remedy issue #203 deleted - it teaches the operator to distrust the message, one layer in. Floor the start, floor the end and add one, so `hi > win_end` always holds and the range is never empty; slight over-cover into the neighbouring window is the safe direction. The test contract asserts the ROUND TRIP - the prescribed range, fed back through the real filter, recovers every cue of the window - not merely that two numbers were formatted.
11. **The marker is written to the tmp file as well as to `parts` (Codex peer pass).** An empty window followed by a later window RAISING never reaches final assembly, so the surviving `.txt.tmp` would hold the later window's partial text with no record that an earlier window was missing entirely - a surface claiming a clean run over a gap, which is precisely what item 6 exists to prevent. The crash path is the one where a reader has ONLY the tmp file.
12. **Operational separation is unchanged** - no `video_intel` import, no config/taxonomy/meta.json read; verified by AST import walk. The captions and video-understanding paths are deliberately untouched: they chunk by their own mechanism, and folding them into this one is a separate decision. Test contract: `tests/test_translate_from_transcript_windows.py`.

**Standalone utility:** `scripts/translate_video.py` — BCS subtitle translation. **This is NOT part of the video-intel pipeline.** It shares the same Gemini API patterns (lazy imports, retry logic, FileData for YouTube URLs) and lives in this repo for convenience, but has no dependency on `video_intel.py`, `config.yaml`, or the scan/transcript/concepts workflow. It has its own CLI args, its own output directory (`./examples` by default), and its own tests. Do not integrate it into the main script or add pipeline features (meta.json, concept extraction, etc.) to it. Default model is `gemini-2.5-pro` (GA, stable, best translation quality and timestamp compliance).

**Translation strategy: SRT-first with video fallback.** The script first tries to fetch the YouTube English caption track via `youtube-transcript-api`, preferring manually authored captions over auto-generated. If captions exist, it sends them to Gemini as a single streaming text-only request — fast (minutes, not tens of minutes), cheap (~10-20K input tokens vs ~400K for video), and immune to the long-video safety-filter soft-stops documented in [ADR-0015](docs/adr/ADR-0015-permissive-safety-filters-for-faithful-reporting.md) and [the journalist-video solution doc](docs/solutions/integration-issues/gemini-soft-stop-political-content-20260411.md). The SRT-first path also writes a raw `.en.srt` sibling file alongside the BCS translation, byte-identical to what you'd get from downsubs.com or `yt-dlp --write-auto-subs`, so you always have an independently reviewable English source even when Gemini fails. The output file's `**Source mode:**` field tells the reader whether the BCS came from a manual caption track, an auto-generated caption track (with silent ASR cleanup), or direct video audio. When the captions track is auto-generated, the SRT prompt instructs Gemini to silently fix punctuation and capitalization as part of the translation pass. Pass `--force-video` to skip the captions check and go straight to video understanding (for testing the fallback or when caption quality is known to be bad). Pass `--srt-only` to write just the `.en.srt` sibling and exit without calling Gemini — useful as a free replacement for third-party subtitle-download sites or when summarizing videos in English only.

**SRT prompt discipline: positive 1:1 count invariant.** The `translate-bcs-from-srt` prompt instructs Gemini to produce exactly N output lines (where N is substituted via `{{INPUT_LINE_COUNT}}`), one per input line, in the same order, with a 1-to-1 correspondence by position. This is **positive framing only** — no "do not invent"/"do not extrapolate" negative rules, because empirical evidence (Phase 4 revert) showed those INCREASED hallucination rather than reducing it. The `test_prompt_has_no_hard_stopping_rule` and `test_prompt_has_no_negative_format_examples` tests in `tests/test_translate_video.py` guard against accidentally reintroducing the bad phrasings.

**Thinking budget caveat on Gemini 2.5 Pro.** The `--thinking-budget N` flag caps the model's internal reasoning tokens via ThinkingConfig. Critical fact: on 2.5 Pro, thinking tokens and output tokens **share** `max_output_tokens` — if thinking burns 28k of the 65k cap, you effectively have only 37k for visible output, which can trigger `MAX_TOKENS` mid-stream on long SRT jobs. 2.5 Pro cannot disable thinking (valid range **128–32768**, confirmed at [ai.google.dev/gemini-api/docs/thinking](https://ai.google.dev/gemini-api/docs/thinking)); 2.5 Flash can (range 0–24576); Gemini 3.x uses `thinking_level` and rejects `thinking_budget` entirely. The SRT path **defaults to `thinking_budget=128`** on 2.5 Pro (constant `SRT_DEFAULT_THINKING_BUDGET`). Empirical testing on a 1h 4min politically sensitive interview showed this eliminated hallucinated content, restored `finish_reason=STOP`, held timestamp drift to <2 minutes local, and cut total tokens by 26%. Pass `--thinking-budget N` to override. The video-understanding fallback path does NOT inherit this default. See `validate_thinking_budget()` for the model-aware range validator.

**Rich-transcript input (`--from-transcript PATH`):** For videos where on-screen content and speaker changes matter (clipped interviews, slide-heavy talks, content with OCR overlays), YouTube SRT alone loses too much context. The two-step manual chain is: (1) `python scripts/video_intel.py transcript --url "URL"` produces a rich markdown transcript with `[MM:SS]` timestamps, speaker labels with roles, `SCREEN [start-end] [type]: description` sections, optional `On-screen text: "..."` OCR lines, and an optional `## Speaker Identification Evidence` footer; (2) `python scripts/translate_video.py --from-transcript PATH/to/file.transcript.md` reads that file and translates it to BCS using the new `translate-bcs-from-transcript` prompt, which preserves every structural marker (timestamps, SCREEN markers, code blocks, markdown) and translates every content field (speech, SCREEN descriptions, OCR, role parentheticals, evidence bullets). The output lands as a `.translate-bcs.txt` sibling next to the input transcript. The path inherits `SRT_DEFAULT_THINKING_BUDGET=128` on 2.5 Pro. The two scripts stay operationally separate — this is a file handoff, not a pipeline merge. Use when captions are poor, missing, when preserving on-screen context is essential to the translation's meaning, or **when the video is long (over ~90 minutes)** where the SRT-first path's chunk math drifts ([issue #49](https://github.com/dzivkovi/video-intel/issues/49)). Validation is permissive: file exists, <500KB, contains at least one `[MM:SS]` line. No structural count canaries or monotonicity checks in v1 — we rely on the same thinking_budget mitigation that fixed the SRT path.

**Video fallback:** When no English captions are available, the script falls through to the video-understanding path. **Token budget:** that path reads audio only — the `translate-bcs` prompt never references on-screen text — so it defaults to low media resolution (~100 tokens/sec, fits videos up to ~170 min in one request). Audio quality is unaffected: `media_resolution` only controls video frame tokens, and audio is tokenized at a fixed 32 tokens/sec regardless. Use `--high-res` (~300 tokens/sec, ~55 min per request) only when a future prompt needs to read slides or burned-in captions. Chunking is resolution-aware: at the default low resolution, videos up to **150 minutes** run as a single request; with `--high-res`, the threshold drops to **50 minutes**. Above the threshold, the script auto-chunks into uniform `--chunk-minutes` (default 20) segments from the start. Part files are the canonical artifacts; `--stitch` merges them into a single file with timestamp normalization, a per-segment coverage table, `<!-- segment ... -->` dividers around non-ok chunks, and partial-translation annotations. Single-request outputs also get a coverage sanity check and a TRUNCATED annotation in the header if Gemini silently stops early. A visible `## ⚠️ Incomplete translation` H2 notice block is emitted before the body whenever observed coverage falls below 95%, with the root cause tailored to the captured `finish_reason` (SAFETY, MAX_TOKENS, STOP, or unknown).
